## ① Intuition Build the Mental Picture

### Why do you need reporting standards?

Imagine reading: "We estimated a cross-lagged network with LASSO." You do not know how λ was chosen, whether the items were standardized, what the seed was, whether there were covariates, how missing data were handled, or which software versions were used. If any one of these differs, the network may differ (Lesson 9.2: just changing the seed makes about 15% of edges "sometimes there, sometimes not"). The goal of reporting standards is that readers can learn every decision that affects the results without having to ask the authors.

### The reporting standards of Burger et al. (2023)

Burger, Isvoranu, Lunansky and colleagues proposed reporting standards for cross-sectional psychological network analysis (published in *Psychological Methods*), covering every stage from the research question and data to estimation, stability and interpretation. There is no official standard for CLPN yet, so this lesson takes the general approach of these standards as a framework, carries it over to the CLPN setting, and adds the elements specific to longitudinal data and nodewise regression: waves and interval, attrition, λ rule, autoregressive edges, out/in-EI and replication. When you write a paper, read the original as well and cite it where needed.

### What is missing from "we estimated it with LASSO"?

At least the following: the estimation framework (nodewise regression, each T2 node on all T1 nodes), whether items were standardized, the λ rule and number of folds, the random seed, covariates and their penalty, software and versions. Only when all of these are written down can readers understand why your network looks the way it does.

### Open science: sharing code and data

- **Code:** upload your R scripts (or Quarto project) to OSF (Open Science Framework) or GitHub and give the link in the paper. The course's script layout (`R/_setup.R` + one script per lesson + `R/output/`) is a good template.

- **Data:** data about service users often cannot be made public. What you can share: the correlation matrix, simulated "synthetic data", or de-identified data within what the ethics approval allows.

- **Software versions (sessionInfo()):** run `sessionInfo()` at the end of the script to record the versions of R and all packages (R/L9-3.R does this for you).

### Preregistration

Preregistration means registering your research question, hypotheses and analysis plan publicly (e.g., on OSF) before you see the data (or the results). The registration is time-stamped and cannot be changed afterwards. It is the strongest tool for limiting researcher degrees of freedom. Even if you do not preregister formally, write a one-page analysis plan before the analysis (Lesson 10.1), and in the paper explain any deviations from the plan and why.

### Special points for social work research

Social work samples often come from a particular agency or community (for example the residents of one neighborhood, or the clients of one agency). When reporting, make the limits of the sample's representativeness clear: whom the conclusions can be generalized to and whom not. If the data come from service records or an intervention program, also state whether the measurements were taken by the service providers themselves (possible social desirability bias), and describe the ethics approval and informed consent. These are not "network methods" topics, but reviewers and practitioners will both care about them.

### Common mistakes

- **"The results were stable" without numbers:** give the actual CS-coefficient and say which index it is (out-EI or in-EI). In the course data, the CS of in-EI is between 0.44 and 0.52 (depending on the run; 0.52 in this run of Lesson 8.3) and out-EI's is only about 0.20, so simply saying "stable" is wrong.

- **Reporting only the significant parts:** unstable results must be reported too; readers need to know which conclusions are not stable.

- **Methods and code disagree:** the paper says lambda.1se, but the code uses the default lambda.min. Check item by item before you submit.

## ② Essential Math Write the Intuition as Equations

The "essential math" in this lesson is which numbers must appear in a report and how to check them against each other.

| Number | Symbol | How to check it |
| --- | --- | --- |
| Sample size (per wave / analyzed) | \(N_1, N_2, N_3,\ N_{\text{analysis}}\) | With listwise deletion \(N_{\text{analysis}}\le \min(N_t)\); otherwise describe the imputation |
| Number of nodes | \(p\) | At most \(p(p-1)\) cross-lagged edges |
| Number of nonzero cross-lagged edges | \(E\) | Density \(=E/[p(p-1)]\) |
| Range of autoregression | \(\min_k\beta_{kk},\ \max_k\beta_{kk}\) | Usually all positive (negative values need explaining) |
| Number of bootstrap replicates | \(B\) | Usually 1,000; fewer than 500 needs explaining |
| CS-coefficients | \(\mathrm{CS}_{\text{out}},\ \mathrm{CS}_{\text{in}}\) | Compare with 0.25 / 0.5 |
| Agreement in sensitivity analysis | \(r\) | Correlation of edge weights between the main and the alternative analysis |

Symbols: \(N_t\) is the sample size at wave \(t\); \(p\) is the number of nodes (items) per wave; \(\beta_{kk}\) is the autoregressive coefficient of node \(k\) (the diagonal of the matrix); \(E\) is the number of nonzero cross-lagged edges; \(B\) is the number of bootstrap resamples.

#### Checking the totals of out-EI and in-EI

\[\sum_k \text{out-EI}_k=\sum_j \text{in-EI}_j=\sum_{k\neq j}\hat\beta_{kj}\]

Each cross-lagged edge \(\hat\beta_{kj}\) is counted exactly once in an out-EI (its start, \(k\)) and once in an in-EI (its end, \(j\)), so the two columns must have the same total. If the totals of the two columns in a table are far apart, the code or the table is wrong (Lesson 7.4).

#### Reporting precision

Edge weights and centrality are usually given to 2–3 decimals, CS-coefficients to 2. In APA style (7th edition), statistics whose absolute value cannot exceed 1 (r, p, proportions, CS-coefficients) are written without a 0 before the decimal point, e.g., r = .52, p = .019, CS = .52; statistics that can exceed 1 (M, SD, unstandardized coefficients B, t, χ²) keep the 0. Standardized coefficients β usually follow the same rule and drop the 0 (β = .14); some journals (Chinese journals often) keep it (β = 0.14). Choose one according to the journal you submit to and use it consistently.

### Worked example: rewriting a weak methods description so others can check it

**Before:** "We estimated a cross-lagged network with LASSO and tested its stability with the bootstrap."

What is missing? A reader cannot tell: which package and version; whether the variables were standardized; how λ was chosen (how many folds, `lambda.min` or `lambda.1se`, which seed); whether covariates were included and whether they were penalized; which centrality indices were used and whether they include autoregressive edges; which bootstrap, and how many resamples; and what standard was used for CS.

**After:** "The cross-lagged panel network was estimated with nodewise LASSO regression (R 4.5, glmnet 4.1-8). All items were z-standardized first; each T2 node was regressed on the 9 T1 nodes, with λ chosen as `lambda.min` by 10-fold cross-validation (set.seed(2026)); gender and age were added as unpenalized covariates in a sensitivity analysis. Centrality was computed as out-expected influence and in-expected influence, plus bridge indices with loneliness and depression as communities, all excluding autoregressive edges. Edge-weight accuracy was assessed with 1000 nonparametric bootstrap resamples, and centrality stability with 1000 case-dropping bootstrap resamples; CS-coefficients used a correlation of ≥ 0.7 in ≥ 95% of samples, and rankings were interpreted only when CS ≥ 0.25. Analysis code and simulated data are in the supplementary material."

The rewritten paragraph is several times longer, but every sentence answers a decision a reader would ask about. Go through this lesson's reporting checklist and confirm each item is covered.

**Common mistakes when writing the methods section**

- **Writing only "default settings were used".** Defaults change between software versions; give the actual values.

- **Not reporting how many people were excluded and why.** Attrition and the handling of missing data need one clear statement (Lesson 4.3).

- **Presenting choices made afterwards as if they were planned.** If an analysis was added after you saw the results, say honestly that it is "exploratory".

A practical test: ask a classmate who was not involved in the analysis to rewrite the code using only your methods section and the data. If they have to ask you about any setting, your methods section is missing it.

Complete companion script `R/L9-3.R` (42 lines, click to expand)

```r
# =====================================================================
# L9-3.R  Reporting Standards: Verifiable Methods & Reproducible Results
#         (Reporting: versions, seeds, settings)
# Automatically generates an "Analysis Information Checklist" suitable for
# direct inclusion in Method sections or Supplementary Materials.
# =====================================================================
source("R/_setup.R")
log_open("L9-3_reporting_info.txt")
pk <- c("glmnet", "qgraph", "bootnet", "networktools", "lavaan", "psych", "tidyverse")
cat("== Software ==\n", R.version.string, "\n")
# Package versions use each package's own specification (the Version field in DESCRIPTION, e.g. "4.1-8" for glmnet).
# as.character(packageVersion(p)) replaces hyphens with dots ("4.1.8"), which diverges from sessionInfo() and CRAN notation.
for (p in pk) cat(sprintf("  %s %s\n", p, utils::packageDescription(p)$Version))
cat("\n== Essential Reporting Elements for CLPN Method Sections (Checklist) ==\n",
"[ ] Data: Sample size, number of waves, time lags, item wording, and scoring\n",
"[ ] Missing data & attrition handling (listwise deletion / multiple imputation / FIML)\n",
"[ ] Standardization: All items z-standardized prior to estimation\n",
"[ ] Estimation: Nodewise LASSO regression of each T2 item on all T1 items (glmnet, alpha = 1)\n",
"[ ] λ selection: 10-fold cross-validation lambda.min (or lambda.1se / EBIC, with gamma = ?)\n",
"[ ] Random seed: set.seed(2026)\n",
"[ ] Covariates and penalty specification (penalty.factor)\n",
"[ ] Centrality: out-EI / in-EI (excluding autoregressive edges), community definitions for bridge EI\n",
"[ ] Stability: Nonparametric bootstrap (number of replications), case-dropping CS-coefficient\n",
"[ ] Sensitivity analyses: λ tuning rules, random seeds, item redundancy trimming, T2→T3 replication\n",
"[ ] Software versions (see above) and code/data sharing repository links (e.g., OSF)\n")
# sessionInfo() enumerates all loaded packages (tidyverse alone attaches dozens), producing an extensive printout.
# The log retains only the opening segment: R version, platform, locale, and directly attached packages,
# truncating before "loaded via a namespace" (typically ~20 lines). Indirectly loaded packages are omitted from the log.
# The full session information is saved separately for supplementary materials.
# Packages must be loaded first so that sessionInfo() classifies them under "other attached packages".
suppressPackageStartupMessages(for (p in pk) library(p, character.only = TRUE))
si <- capture.output(print(sessionInfo()))
# In the public course repository, local BLAS/LAPACK paths, locale, and timezone strings (Matrix products ... tzcode) are omitted.
# In your own research, you do not need to omit these: they facilitate reproduction; decide beforehand whether you wish to disclose them.
a <- grep("^Matrix products", si)[1]; b <- grep("^attached base packages", si)[1]
if (!is.na(a) && !is.na(b) && b > a) si <- c(si[seq_len(a - 1)], "(Local paths, locale, and timezone omitted)", "", si[b:length(si)])
writeLines(si, out("sessionInfo_full.txt"))
k <- grep("^loaded via a namespace", si)[1]
n_show <- if (is.na(k)) min(25, length(si)) else k - 1
cat("\n== sessionInfo() (first ", n_show, " lines; full ", length(si), " lines in R/output/sessionInfo_full.txt) ==\n", sep = "")
cat(head(si, n_show), sep = "\n")
log_close()
```

## ④ Concept Check Instant Check

Why report R package versions and the random seed?

- A. It is a journal formatting requirement

- It is not just formatting: without them, nobody can reproduce your results.

- B. Different versions and seeds can give different results (especially weak edges and the choice of λ); only when they are reported can others reproduce the results exactly (Correct)

- Correct.

- C. To look professional

- The point is not to look professional but to let others reproduce the work.

- D. There is no need: the same data always give the same results

- Plausible but wrong: Lesson 9.2 showed that with the same data, just changing the seed makes about 15% of edges come and go.

If a CLPN Methods section says only "estimated with LASSO", what key information is missing?

- A. Only the software name

- The software name is only one item; without the λ rule and seed, the analysis still cannot be reproduced.

- B. The estimation framework (nodewise regression), standardization, λ rule and folds, seed, covariates and penalty, software versions, etc. (Correct)

- Correct.

- C. Only the sample size

- The sample size is usually already given in the sample section; what is missing are the estimation settings.

- D. Nothing: LASSO is a standard procedure

- LASSO has many settings to choose (λ rule, folds, standardization, whether covariates are penalized), and each one changes the network.

Which of these is not a common CLPN sensitivity analysis?

- A. Switching to lambda.1se

- It is one: try another reasonable λ rule and see whether the conclusions hold.

- B. Adding covariates

- It is one: it changes the choice of which variables to control for.

- C. T2→T3 replication

- It is one (replication): take another interval and see whether the network is similar.

- D. Raising the bootstrap replicates from 1,000 to 5,000 to steady the interval endpoints (Correct)

- Correct: more replicates only reduce Monte Carlo error and change no analysis decision, so it is not a sensitivity analysis.

What is the main purpose of preregistration?

- A. To make the paper easier to publish

- Some journals welcome preregistration, but that is not its purpose.

- B. To fix the analysis plan before seeing the results, limiting researcher degrees of freedom (Correct)

- Correct.

- C. To replace ethics approval

- Preregistration and ethics approval are two separate things; you need both.

- D. To increase statistical power

- Power depends on sample size and effect size; preregistration does not change it.

Data about service users cannot be made public. What can you do?

- A. Share nothing

- Materials that contain no personal information, such as code and the correlation matrix, can still be shared.

- B. Share the code, the correlation matrix or synthetic data, and de-identified data within what ethics approval allows (Correct)

- Correct.

- C. Delete names and ID numbers and publish the raw data

- Removing direct identifiers is often not enough: age, gender, neighborhood and so on can identify a person in combination; whether you can publish depends on the scope of the ethics approval and informed consent.

- D. Just write "data available from the authors on request" in the paper

- You can write this, but it does not replace what you can share directly (code, correlation matrix, synthetic data).

## Summary Key Takeaways & Further Reading

- Goal of reporting standards: readers learn every decision that affects the results without having to ask the authors.

- Use the cross-sectional standards of Burger et al. (2023) as a framework, carry them over and add the elements specific to CLPN.

- Must report: data and interval, missing data/attrition, standardization, nodewise LASSO, λ rule, seed, covariates, centrality definitions, bootstrap and CS, sensitivity analyses, software versions.

- Open science: share code (OSF/GitHub), sessionInfo(), preregistration or analysis plan.

- Checks: total out-EI = total in-EI; number of edges ≤ p(p−1).
